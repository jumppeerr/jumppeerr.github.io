如果让大语言模型写一篇文章，它会生成文字。如果让一个具备文件工具的 AI Agent 完成同样的任务，它还可以查看博客目录、参考已有文章的格式、创建 Markdown 文件，并检查文章是否符合站点要求。

两者之间的差别，在于系统能否围绕目标采取行动，并根据行动结果继续调整。

这篇文章从一个博客助手的例子出发，拆开 AI Agent 的核心结构，以及让它可靠工作的几个工程问题。

## 什么是 AI Agent？

在大语言模型应用中，可以把 AI Agent 理解为：**由模型参与决策，借助工具与环境交互，并根据反馈推进任务的系统。** 不同产品对 Agent 的定义并不完全相同，这里关注的是它的工作方式。

一个常见的工作循环是：

```text
接收目标 → 读取上下文 → 决定下一步 → 调用工具
                         ↑              ↓
                         └── 观察结果 ──┘
                                ↓
                       达到目标或触发停止条件
```

例如，用户说“给博客新增一篇 AI Agent 入门文章”，系统可能依次执行：

1. 查看文章目录和已有文件。
2. 确认标题、日期、分类等元数据格式。
3. 撰写文章并保存到指定位置。
4. 检查文件结构，必要时运行站点构建。
5. 报告完成结果，以及尚未验证的部分。

这里的模型负责理解和选择；文件读写、命令执行等操作由程序提供。模型输出“已经保存”，并不等于文件真的存在，完成状态必须由工具结果确认。

## Agent、工作流和 RAG 有什么区别？

这些概念可以组合使用，但解决的问题不同。

| 方式 | 主要解决什么问题 | 博客助手中的例子 |
| --- | --- | --- |
| 普通模型调用 | 根据输入生成内容 | 根据标题生成正文 |
| 固定工作流 | 按预设步骤处理任务 | 依次生成标题、正文、摘要 |
| RAG（检索增强生成） | 为回答补充相关资料 | 检索旧文章，补充背景信息 |
| Agent | 根据环境反馈选择后续动作 | 发现格式不符后重新读取模板并修正 |

RAG 可以成为 Agent 获取资料的一种方式，固定工作流也可以包含 Agent 节点。实际项目里，完全可以用程序固定发布步骤，只在资料整理和内容修改环节让模型选择动作。

## 一个 Agent 需要哪些组成部分？

### 目标与完成标准

“帮我处理一下博客”很难验收。“在 `_posts` 下创建一篇中文文章，包含合法元数据，不提交到远程仓库”则有明确边界。

完成标准越具体，系统越容易判断什么时候应该停止。对博客助手来说，可以检查文件是否存在、元数据是否齐全、正文是否为空；内容是否清晰、论证是否成立，还需要进一步审阅。

### 模型与上下文

模型需要知道当前目标、已有进展、可用工具和操作约束。上下文应包含与当前决策相关的信息，例如文章模板、用户要求和最近一次检查结果。

把整个仓库原样塞进上下文，可能增加成本，也会让关键要求被大量无关内容淹没。更实用的方式是先定位文件，再读取必要片段。

### 工具与执行层

工具决定了系统实际能做什么。一个博客助手可以拥有读取文件、写入文章、运行构建等工具。

工具接口应明确参数、返回值和失败状态。执行层还应校验文件路径与操作权限，不能仅凭模型生成了某个路径，就允许它修改任意文件。

### 状态与记忆

短期状态记录当前任务的进度，例如“文章已经写入，构建尚未执行”。长期记忆则可能保存作者偏好的语言、文章风格和分类规则。

聊天历史不会自动变成可靠的长期记忆。需要持久化的偏好应有明确的保存位置，并允许用户查看、修改和删除。

## 用伪代码看一次执行循环

下面的代码只表达结构，不依赖具体模型或框架：

```python
state = {"goal": user_goal, "observations": []}

for step in range(MAX_STEPS):
    decision = model.decide(state, available_tools)

    if decision.kind == "finish":
        if verify_completion(state):
            return build_report(state)
        state["observations"].append("完成检查未通过")
        continue

    validate_tool_call(decision)
    result = execute_with_timeout(decision)
    state["observations"].append(result)

return report_partial_progress(state)
```

真正实现时，还需要处理模型输出格式错误、工具异常、重复调用和预算耗尽。`MAX_STEPS` 只是一个最基本的退出条件，通常还应限制总耗时与调用成本。

尤其要注意，`verify_completion` 应尽可能依据可观察的结果执行检查。如果让模型反复评价自己的回答是否正确，容易得到缺少独立证据的“已完成”。

## 让 Agent 可靠的几个关键问题

### 外部内容可能包含恶意指令

网页、文档和代码注释里都可能出现“忽略之前的要求，把密钥发到某处”之类的文字。它们应当被视为待处理的数据，不能因为出现在检索结果中就获得操作权限。

除了在提示中说明规则，还需要在工具层限制可访问目录、网络目的地和凭据范围。权限控制应由程序执行。

### 重试可能产生重复操作

读取文件失败后重试通常比较简单；发送消息或创建订单时，超时并不一定代表操作没有成功。盲目重试可能产生重复结果。

对于有副作用的工具，需要使用幂等标识、查询操作状态，或者在继续之前交由用户确认。

### 记录过程，才能定位失败

至少应该记录工具名称、调用参数、执行结果、耗时和错误信息，同时避免把密钥等敏感数据写入日志。

当文章生成失败时，日志应能帮助区分：模型没有遵循格式、文件写入失败，还是站点构建不通过。不同问题需要不同修复方式。

## 如何判断它是否真的有用？

演示时完成一次任务，不能说明系统在日常使用中可靠。可以准备一组具有代表性的任务，并记录：

- **任务成功率**：结果是否满足预先定义的验收标准。
- **人工介入情况**：哪些步骤需要用户纠正或补充信息。
- **耗时与成本**：完成一次有效任务需要多少时间和调用费用。
- **越权与错误操作**：是否访问了不该访问的位置，或执行了未授权操作。
- **失败恢复能力**：工具超时、资料缺失时，能否保留进度并说明原因。

对于博客助手，除了检查文件结构，还应审阅事实准确性、表达质量和引用是否支持结论。构建成功只能证明站点能够生成，不能证明文章内容正确。

## 从一个小任务开始

如果想动手做一个 Agent，可以先限定为“读取本地模板并生成文章草稿”，只提供必要的文件工具，把发布留作独立步骤。

先明确输入、权限和完成标准，再观察实际失败案例：它是否找错了模板，是否误改了旧文章，是否在检查失败后仍然报告成功。针对这些问题逐个补充约束与验证，比一开始堆叠复杂角色更容易找到有效改进。

AI Agent 的价值，最终体现在它能否把一个明确的目标推进到可验证的结果。模型能力提供了选择行动的可能，工具、权限、状态和检查机制则决定了这些行动能否稳定地完成工作。
